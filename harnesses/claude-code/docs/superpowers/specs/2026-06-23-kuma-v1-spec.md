# Kuma v1 Spec

## Goal

Build a Claude Code plugin named `Kuma` that delegates code review and general task execution to alternative model backends while keeping Claude Code as the coordinator.

Kuma v1 is intentionally lean. It reuses the working shape of `codex-plugin-cc`, follows local `harnesses/claude-code/` conventions, and only changes the parts required by the approved product decisions.

## Product Positioning

Kuma is not a generic provider browser in v1.

It is a focused Claude Code plugin for three product targets:
- `opencode-go`
- OpenCode Zen (CLI slug: `opencode` — "opencode-zen" is a marketing name, not a provider slug either backend recognizes)
- `ollama-cloud`

Claude Code remains the brain and coordination layer. Kuma is the bridge that sends work to other model runtimes and brings results back into chat.

See "Provider ↔ backend matrix" under Architecture for exactly which backend(s) reach each target.

## Locked Decisions

### Public command surface

Kuma v1 exposes exactly these commands:
- `/kuma:setup`
- `/kuma:models`
- `/kuma:review`
- `/kuma:task`
- `/kuma:status`
- `/kuma:result`
- `/kuma:cancel`

Not in v1:
- `/kuma:transfer`
- `/kuma:rescue`
- `/kuma:adversarial-review`

`/kuma:review` remains the single review entrypoint.

Review modes:
- default: normal review
- `--mode adversarial`: adversarial framing

The current Codex review setup, prompts, and script philosophy should be kept as closely as possible for v1.

### Runtime model

Kuma v1 uses two interchangeable backend adapters:
- `opencode`
- `pi`

The user may choose a backend per command with `--backend`.

Kuma v1 does not implement:
- smart backend routing
- deep backend-native session control beyond simple resume (see below)
- multi-turn session management as a first-class product surface

Claude Code remains the orchestrator. Each backend invocation is a one-shot CLI call (`opencode run ...` / `pi -p ...`); Kuma does not run a long-lived server or RPC daemon for either backend in v1.

Continuation across invocations is a thin pass-through, not custom session management: Kuma persists the backend's own native session handle (opencode's `--session`/`--continue`/`--fork`, pi's `--session`/`--continue`/`--resume`) per workspace, and replays it when `--resume` is used or when continuing the last relevant run is safe. Kuma does not interpret or manage session contents itself.

### Defaults

`/kuma:setup` may configure:
- default backend
- default model

Command flags always override configured defaults.

If a required default is missing and the user does not pass the flag explicitly, Kuma should fail clearly and point the user to `/kuma:setup`.

## Architecture

Kuma should follow this structure:

1. Plugin shell under `harnesses/claude-code/plugins/kuma/`
2. Local bridge runtime script (`kuma-companion.mjs`)
3. Thin backend adapters (`opencode`, `pi`)
4. Small persistent local job/config store
5. Review prompt layer derived from Codex

### Baseline strategy

Use:
- `.reference/codex-plugin-cc/plugins/codex/` (a persistent local clone of `https://github.com/openai/codex-plugin-cc`, gitignored at the repo root, refreshed with `git pull` as needed) as the behavioral reference
- local `harnesses/claude-code/` plugin conventions as the structural/distribution reference

The reference clone lives outside this repo's tracked history. Porting means copying/adapting the needed files directly into `harnesses/claude-code/plugins/kuma/` during implementation; once that copy is done, the repo has no further runtime dependency on the reference clone.

This means Kuma v1 should:
- keep the Codex plugin shell shape where practical
- keep the Codex review behavior where practical
- simplify the public command surface
- add Kuma-native discovery and status improvements

### Provider ↔ backend matrix

Verified against the locally installed CLIs (`pi` v0.80.2, `opencode` v1.17.11):

| Target (display name) | CLI provider slug | via `pi` | via `opencode` |
|---|---|---|---|
| OpenCode Go | `opencode-go` | yes | yes |
| OpenCode Zen | `opencode` | yes | yes |
| Ollama Cloud | `ollama-cloud` | no | yes (requires Ollama configured separately) |

Notes:
- `opencode-zen` is never a real CLI slug in either tool; the slug is `opencode` in both. Kuma's model index and `--backend`/model selection must use `opencode`, not `opencode-zen`.
- `ollama-cloud` is reachable only through the `opencode` backend in v1; `pi` has no Ollama support. Kuma should fail clearly (pointing to `/kuma:setup`) if a user requests `ollama-cloud` via `--backend pi`.
- Additional providers each backend supports (many Chinese/European vendors: `deepseek`, `zai`, `kimi-coding`, `mistral`, `minimax`, `xiaomi` variants, and 70+ more via `opencode`) are out of scope for v1 — see Future Work.

## Command Reference

### `/kuma:setup`

Responsibilities:
- verify backend binary availability for `opencode` and `pi`
- verify auth readiness per backend, per provider:
  - `pi`: `OPENCODE_API_KEY` (covers the `opencode`/`opencode-go` providers) and `~/.pi/agent/auth.json` for its other providers
  - `opencode`: `~/.local/share/opencode/auth.json`, plus the `opencode-go` cookie/quota file and env vars, checked via `opencode providers list`
  - `ollama-cloud`: confirm Ollama itself is configured (this is an `opencode`-only target in v1); fail clearly if not, rather than silently omitting it from `/kuma:models`
- refresh the local latest-model index (via each backend's own model listing)
- optionally set default backend and default model

It should not become a heavy diagnostic tool in v1.

### `/kuma:models`

Responsibilities:
- show only models Kuma can actually use in v1
- use the local normalized model index
- keep output compact

Output shape is a single flat table with exactly these columns:
- `model`
- `provider`
- `backend`
- `capabilities`
- `context`
- `status`

It should show only rows for:
- `opencode-go`
- `opencode` (OpenCode Zen)
- `ollama-cloud`

No extra pricing, long descriptions, or raw metadata in v1 output.

### `/kuma:review`

Responsibilities:
- perform a normal code review by default
- perform adversarial review when `--mode adversarial` is used
- preserve Codex review setup and prompting style as much as possible
- support foreground (`--wait`) and background (`--background`) execution using the same inline pattern Codex's `review.md`/`status.md` use: the command file itself launches `kuma-companion.mjs` via Claude Code's native `Bash(..., run_in_background: true)` when backgrounding, with no bundled skill or subagent involved
- when neither flag is passed, estimate review size from `git status`/`git diff --shortstat` the same way Codex's `review.md` does, and ask the user to choose foreground or background
- if the backend's output does not conform to the review JSON schema, render it as raw text rather than failing — schema conformance is best-effort, especially for smaller/non-Codex models
- return backend output back into Claude chat

It remains read-only. Kuma does not apply changes during review.

### `/kuma:task`

Responsibilities:
- serve as the single generic delegation command
- forward implementation, debugging, research, or follow-up tasks to the chosen backend/model
- return results back into Claude chat
- persist enough metadata for status/result/cancel and simple resume behavior

Recommended v1 flags:
- `--model`
- `--backend`
- `--wait`
- `--background`
- `--resume`
- `--fresh`

If the user does not choose `--resume` or `--fresh`, Kuma may continue the last relevant run for the current workspace when that is obvious and safe.

### `/kuma:status`

Kuma v1 status is operator-focused.

Default columns:
- `id`
- `task kind`
- `provider`
- `model`
- `backend`
- `phase`
- `resumable`
- `result ready`

The `phase` column shows the authoritative 5-value status (`queued`/`running`/`done`/`error`/`cancelled`); any best-effort progress hint (see State And Job Lifecycle) is shown only in the single-job detail view via `/kuma:result`, not in the compact table.

This command is intentionally more operational than Codex status.

### `/kuma:result`

Shows the final stored output for a finished run.

### `/kuma:cancel`

Cancels an active run by terminating the one-shot backend process (and its child process tree), then marks the job `cancelled` in local state. There is no backend-native RPC interrupt to send in v1 — neither backend runs as a persistent server, so a process-tree kill is the entire mechanism.

## Backend Adapters

Kuma v1 supports two backend adapters, both invoked as one-shot CLI calls — no HTTP server, no stdio-RPC daemon, no broker/lifecycle process in v1:

- `opencode`:
  - prompt submission: `opencode run -m <provider>/<model> --format json "<prompt>"`
  - model discovery: `opencode models [provider]`
  - auth: `opencode providers login` / `~/.local/share/opencode/auth.json`
- `pi`:
  - prompt submission: `pi -p --mode json --model <provider>/<model> "<prompt>"`
  - model discovery: `pi --list-models [search]`
  - auth: `~/.pi/agent/auth.json` / `OPENCODE_API_KEY` (for the `opencode`/`opencode-go` providers)

The adapter layer should be thin.

Its purpose is to normalize:
- model selection
- prompt submission
- status/result retrieval (parsed from the one-shot process's stdout/exit code, plus the persisted job record)
- auth/model discovery

Cancellation is a process-tree kill of the running one-shot invocation (matching the reference implementation's fallback path) — there is no RPC-level interrupt to send in v1 since neither backend runs as a persistent server.

It should not attempt to fully unify all backend-native session behavior in v1.

## Model Metadata

### Primary source

Primary source for model metadata is each backend's own live listing:
- `opencode models [provider]`
- `pi --list-models [search]`

Reason:
- these are live, authoritative answers to "what can Kuma actually reach right now" — auth-gated and provider-scoped
- neither of the fields Kuma needs most (`backend`, live `status`) exists in any third-party catalog; only the backends themselves can answer them

### Optional enrichment source

`https://basellm.github.io/llm-metadata/api/newapi/models.json` (+ companion `vendors.json`) MAY be used to enrich entries with pricing/context-window/capability hints, but only as an optional overlay, never as the source of truth for availability.

Caveats, confirmed by inspecting the live endpoint:
- it is a NewAPI pricing catalog: fields are `model_name`, `vendor_name`, `tags`, `status`, and `price_per_m_*`/`ratio_*` cost fields
- `vendor_name` is a display name ("OpenCode Zen", "OpenCode Go", "Ollama Cloud"), not a CLI slug — needs a slug map before it can join backend data
- `capabilities` and `context` are not structured fields; they are comma-joined tokens inside the freeform `tags` string (e.g. `"Reasoning,Tools,Vision,1M"`) and must be parsed
- `status` here is a static catalog flag, not live availability
- `pydantic/genai-prices` is dropped as a required backup source for v1 (it is pricing-only, weaker than BaseLLM for this purpose); it may still be referenced later purely for cost display

### Local latest-model index

Kuma maintains a local normalized latest-model index built from backend self-report.

Refresh behavior in v1:
- refreshed during `/kuma:setup` (via `opencode models --refresh` / `pi --list-models` under the hood)
- read by `/kuma:models`
- cached locally so `/kuma:models` stays fast and deterministic
- filtered to the three v1 targets using the provider ↔ backend matrix (see Architecture)

### Stored and displayed fields

For v1, the local index stores and displays the same compact fields:
- `model` — from the backend's own model id
- `provider` — the CLI slug (`opencode-go`, `opencode`, `ollama-cloud`), not a display name
- `backend` — which adapter(s) can reach it (`opencode`, `pi`, or both); this is Kuma-synthesized, not sourced from any upstream metadata
- `capabilities` — populated from BaseLLM enrichment when available (parsed from `tags`), otherwise omitted
- `context` — populated from BaseLLM enrichment when available (parsed from `tags`), otherwise omitted
- `status` — live availability as reported by the backend's own listing/auth check, not a static catalog flag

Anything richer is deferred to future `/kuma:models` subcommands or expanded views.

## State And Job Lifecycle

Kuma maintains a small local state store for:
- configured defaults
- active/recent jobs
- result availability
- simple resume metadata

### Storage model

State is stored per-workspace, not in one global file.

Kuma resolves a workspace-scoped state directory the same way Codex's `state.mjs` does:
- hash the resolved workspace root
- key the state directory by `<slug>-<hash>` under a Kuma data root (env override, falling back to `~/.kuma/`)
- keep jobs and job logs inside that per-workspace directory

This keeps `--resume` and "continue the last relevant run for the current workspace" correct when the user has multiple repositories in flight. Kuma v1 does not offer any cross-workspace job listing, search, or aggregation — see Future Work.

### Concurrency and retention

Kuma v1 allows at most one active background job per workspace at a time; a second `--background` request while one is already running is rejected with a pointer to `/kuma:status`/`/kuma:cancel`, not silently queued.

Job history is pruned per workspace (matching the reference implementation's bounded job count) rather than kept forever.

### Status phases

The authoritative, durable status is a 5-value set matching what a one-shot CLI invocation can actually distinguish (proven in the reference implementation, which uses this same 5-value set internally):
- `queued`
- `running`
- `done`
- `error`
- `cancelled`

Kuma MAY additionally surface a best-effort, non-authoritative progress hint (e.g. "preparing", "waiting on backend") inferred from process output while `running`, the same way the reference implementation infers finer phases from log lines. This hint is cosmetic only — `/kuma:status` and `/kuma:result` must never depend on it for correctness, only on the 5-value status.

## Non-goals For v1

Kuma v1 does not include:
- transcript transfer / handoff
- public rescue command
- smart routing
- llm-council / multi-model review
- richer `/kuma:models` filtering/search/compare subcommands
- deeper backend-native session control
- full backend session browsing/management
- cross-workspace job visibility, search, or aggregation
- bundled skills or a plugin-internal subagent (background execution is handled inline in each command file via Claude Code's native `Bash(..., run_in_background: true)`, the same mechanism Codex's `review.md`/`status.md` use — no skill or subagent lookup is needed)

## Future Work

The following belong in future versions and should be called out explicitly in docs and planning:

1. `/kuma:transfer`
Claude transcript handoff and richer continuation workflows.

2. Smart routing
Backend/model selection based on task type, cost, or availability.

3. LLM council / multi-model review
Research and productize council-style review flows, including ideas inspired by `llm-council` style projects.

4. Richer `/kuma:models` subcommands
Filtering, searching, comparing, and richer metadata views.

5. Deeper backend-native session control
Expose more of each backend's session/thread controls once the product direction is clear.

6. Cross-workspace job visibility
Listing, searching, or aggregating jobs across multiple workspaces from a single command, once the per-workspace-hashed state model is proven in v1.

7. Additional providers
Extend beyond the three v1 targets to the wider provider sets each backend already supports — e.g. `pi`'s `deepseek`, `mistral`, `zai`, `kimi-coding`, `minimax`, `xiaomi` variants, and 20+ others; `opencode`'s 70+ providers via models.dev. Chinese and European provider coverage is a specifically named near-term follow-on.

## Implementation Direction

The first implementation move should be:
- create `harnesses/claude-code/plugins/kuma/` as the local working plugin folder
- copy the relevant parts of `.reference/codex-plugin-cc/plugins/codex/` there as a reference snapshot
- then prune, rename, and repoint from inside the repo

That keeps Kuma grounded in known-working behavior while we narrow the surface to the approved v1 product.
