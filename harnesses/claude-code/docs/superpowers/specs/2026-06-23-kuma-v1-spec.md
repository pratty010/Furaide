# Kuma v1 Spec

## Goal

Build a Claude Code plugin named `Kuma` that delegates code review and general task execution to alternative model backends while keeping Claude Code as the coordinator.

Kuma v1 is intentionally lean. It reuses the working shape of `codex-plugin-cc`, follows local `claude-code/` conventions, and only changes the parts required by the approved product decisions.

## Product Positioning

Kuma is not a generic provider browser in v1.

It is a focused Claude Code plugin for three product targets:
- `opencode-go`
- `opencode-zen`
- `ollama-cloud`

Claude Code remains the brain and coordination layer. Kuma is the bridge that sends work to other model runtimes and brings results back into chat.

## Locked Decisions

### Public command surface

Kuma v1 exposes exactly these commands:
- `/kuma:setup`
- `/kuma:models`
- `/kuma:review`
- `/kuma:task`
- `/kuma:status`
- `/kuma:result`
- `/kuma:cancel`

Not in v1:
- `/kuma:transfer`
- `/kuma:rescue`
- `/kuma:adversarial-review`

`/kuma:review` remains the single review entrypoint.

Review modes:
- default: normal review
- `--mode adversarial`: adversarial framing

The current Codex review setup, prompts, and script philosophy should be kept as closely as possible for v1.

### Runtime model

Kuma v1 uses two interchangeable backend adapters:
- `opencode`
- `pi`

The user may choose a backend per command with `--backend`.

Kuma v1 does not implement:
- smart backend routing
- deep backend-native session control
- multi-turn session management as a first-class product surface

Claude Code remains the orchestrator. Backend work is treated as effectively stateless from the user's point of view in v1.

### Defaults

`/kuma:setup` may configure:
- default backend
- default model

Command flags always override configured defaults.

If a required default is missing and the user does not pass the flag explicitly, Kuma should fail clearly and point the user to `/kuma:setup`.

## Architecture

Kuma should follow this structure:

1. Plugin shell under `claude-code/plugins/kuma/`
2. Local bridge runtime script (`kuma-companion.mjs`)
3. Thin backend adapters (`opencode`, `pi`)
4. Small persistent local job/config store
5. Review prompt layer derived from Codex

### Baseline strategy

Use:
- `codex-plugin-cc/plugins/codex/` as the behavioral reference
- local `claude-code/` plugin conventions as the structural/distribution reference

This means Kuma v1 should:
- keep the Codex plugin shell shape where practical
- keep the Codex review behavior where practical
- simplify the public command surface
- add Kuma-native discovery and status improvements

## Command Reference

### `/kuma:setup`

Responsibilities:
- verify backend binary availability for `opencode` and `pi`
- verify auth readiness for the three v1 product targets
- refresh the local latest-model index
- optionally set default backend and default model

It should not become a heavy diagnostic tool in v1.

### `/kuma:models`

Responsibilities:
- show only models Kuma can actually use in v1
- use the local normalized model index
- keep output compact

Output shape is a single flat table with exactly these columns:
- `model`
- `provider`
- `backend`
- `capabilities`
- `context`
- `status`

It should show only rows for:
- `opencode-go`
- `opencode-zen`
- `ollama-cloud`

No extra pricing, long descriptions, or raw metadata in v1 output.

### `/kuma:review`

Responsibilities:
- perform a normal code review by default
- perform adversarial review when `--mode adversarial` is used
- preserve Codex review setup and prompting style as much as possible
- return backend output back into Claude chat

It remains read-only. Kuma does not apply changes during review.

### `/kuma:task`

Responsibilities:
- serve as the single generic delegation command
- forward implementation, debugging, research, or follow-up tasks to the chosen backend/model
- return results back into Claude chat
- persist enough metadata for status/result/cancel and simple resume behavior

Recommended v1 flags:
- `--model`
- `--backend`
- `--wait`
- `--background`
- `--resume`
- `--fresh`

If the user does not choose `--resume` or `--fresh`, Kuma may continue the last relevant run for the current workspace when that is obvious and safe.

### `/kuma:status`

Kuma v1 status is operator-focused.

Default columns:
- `id`
- `task kind`
- `provider`
- `model`
- `backend`
- `phase`
- `resumable`
- `result ready`

This command is intentionally more operational than Codex status.

### `/kuma:result`

Shows the final stored output for a finished run.

### `/kuma:cancel`

Cancels an active run and marks it accordingly in local state.

## Backend Adapters

Kuma v1 supports:
- `opencode serve` via HTTP
- `pi --mode rpc` via stdio JSON-RPC

The adapter layer should be thin.

Its purpose is to normalize:
- model selection
- prompt submission
- status/result retrieval
- auth/model discovery

It should not attempt to fully unify all backend-native session behavior in v1.

## Model Metadata

### Primary source

Primary source for model metadata:
- `https://basellm.github.io/llm-metadata/api/newapi/models.json`

Companion vendor source:
- `https://basellm.github.io/llm-metadata/api/newapi/vendors.json`

Reason:
- it is GitHub-hosted
- it includes vendor-oriented metadata
- it maps well to the product targets the user cares about

### Backup source

Backup source:
- `pydantic/genai-prices`

Use it only when:
- BaseLLM is missing needed fields
- BaseLLM fetch fails
- Kuma needs a fallback during index refresh

### Local latest-model index

Kuma maintains a local normalized latest-model index.

Refresh behavior in v1:
- refreshed during `/kuma:setup`
- read by `/kuma:models`
- cached locally so `/kuma:models` stays fast and deterministic

### Stored and displayed fields

For v1, the local index stores and displays the same compact fields:
- `model`
- `provider`
- `backend`
- `capabilities`
- `context`
- `status`

Anything richer is deferred to future `/kuma:models` subcommands or expanded views.

## State And Job Lifecycle

Kuma maintains a small local state store for:
- configured defaults
- active/recent jobs
- result availability
- simple resume metadata

### Status phases

User-facing phases are:
- `queued`
- `preparing`
- `executing`
- `waiting`
- `done`
- `error`
- `cancelled`

These are intentionally user-meaningful rather than backend-native.

## Non-goals For v1

Kuma v1 does not include:
- transcript transfer / handoff
- public rescue command
- smart routing
- llm-council / multi-model review
- richer `/kuma:models` filtering/search/compare subcommands
- deeper backend-native session control
- full backend session browsing/management

## Future Work

The following belong in future versions and should be called out explicitly in docs and planning:

1. `/kuma:transfer`
Claude transcript handoff and richer continuation workflows.

2. Smart routing
Backend/model selection based on task type, cost, or availability.

3. LLM council / multi-model review
Research and productize council-style review flows, including ideas inspired by `llm-council` style projects.

4. Richer `/kuma:models` subcommands
Filtering, searching, comparing, and richer metadata views.

5. Deeper backend-native session control
Expose more of each backend's session/thread controls once the product direction is clear.

## README And Documentation Updates Required

Kuma v1 should explicitly update or create the following docs:

1. `claude-code/plugins/kuma/README.md`
User-facing install, setup, command reference, backend/model matrix, and usage examples.

2. `claude-code/docs/superpowers/plans/2026-06-23-kuma-v1.md`
Must be rewritten to match this locked lean-v1 scope.

3. Any root or component README that mentions available Claude Code plugins
Should mention Kuma alongside existing plugin offerings once Kuma exists.

4. Command docs under `claude-code/plugins/kuma/commands/`
Must reflect the lean surface and the single review command with `--mode adversarial`.

## Implementation Direction

The first implementation move should be:
- create `claude-code/plugins/kuma/` as the local working plugin folder
- copy the Codex plugin there as a reference snapshot
- then prune, rename, and repoint from inside the repo

That keeps Kuma grounded in known-working behavior while we narrow the surface to the approved v1 product.
